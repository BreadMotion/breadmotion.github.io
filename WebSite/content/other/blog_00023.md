今回は Zed の `settings.json`（グローバル設定 & プロジェクト設定）について私が普段使っているおすすめ設定項目を共有します！  
前回のZed関係の記事は [こちら](blog/blog_00017.html）  

## 基本方針

1. 「プロジェクト単位で設定したいものは」はプロジェクトの `.zed/settings.json` に置く
  （例：inlay hints の細かいチューニング、ファイル除外）  
2. 「環境全体で一貫させたいもの」はグローバルの setting.json に置く
  （例：エディタテーマ、フォント、ターミナル実行ファイル） 

上記は担保する予定ですが、プロジェクトやチーム、環境によって最適解が変わってくるので  
各々でカスタマイズするべきではあります。 
ですので、あくまでおすすめです。  

且つ実際の設定パラメータについても上記理由と同等なので調整してみてください。　　
項目の紹介という括りで見てもらえますと。  

## プロジェクト側のおすすめ設定

```json
{
  // コーディングするときに便利
  "inlay_hints": {
    "enabled": true,
    "show_type_hints": true,
    "show_parameter_hints": true,
    "show_other_hints": true,
    "edit_debounce_ms": 700,
    "scroll_debounce_ms": 50
  },
  "file_scan_exclusions": [
    // プロジェクトを編集するときに不要なファイルやディレクトリを記入
    "*.png",
    "*.dll",
    "filename.extension",
    "directory_name",
    "*/directory_name"
  ]
}
```

**ポイントと理由** ：
- `inlay_hints.enabled: true`：
  型情報やパラメータヒントがすぐ見えるのでリファクタやレビューが速くなります。
  特に大型プロジェクトでは型ヒントがあるだけで追跡コストが下がります。
  edit / scroll の debounce は 描画パフォーマンスとレスポンスのバランスで調整（上例は実用的な中間値）。
- `file_scan_exclusions`：
  編集する必要のないものを検索対象から除外することで検索・インデックス処理が高速化されます。
  サードパーティモジュールや見る必要のないものを設定しましょう。

**運用上の注意** ：
  大きい除外リストは CI やコード検索ツールとの整合性に影響することがあるため、チームなどで利用するときは除外ルールの明記など対策をすることを推奨します。  

## グローバルのおすすめ設定

```json
{
  // ブラケットの色分け（読みやすさ向上）
  "colorize_brackets": true,

  // 普段使いするターミナルへのパスを設定
  "terminal": {
    "dock": "right",
    "shell": {
      "program": "file to path\\bash.exe"
    }
  },

  // 普段使いするエージェント設定（AI）
  "agent": {
    "inline_assistant_model": {
      "provider": "copilot_chat",
      "model": "gpt-5-mini"
    },
    "always_allow_tool_actions": true,
    "default_profile": "write",
    "default_model": {
      "provider": "copilot_chat",
      "model": "gemini-3-pro-preview"
    },
    "model_parameters": []
  },

  // LSPの実行パスなどを指定（環境依存）
  "lsp": {
    "omnisharp": {
      "initialization_options": {
        "AnalyzeOpenDocumentsOnly": false,
        "EnableRoslynAnalyzers": true,
        "EnableImportCompletion": true
      }
    },
    "clangd": {
      "binary": {
        "path": "file to path\\clangd.exe",
        "arguments": []
      }
    }
  },

  "languages": {
    "CSharp": {
      "language_servers": ["omnisharp", "!csharp-ls"],
      "format_on_save": "on",
      "tab_size": 4,
      "preferred_line_length": 120
    },
    "JSON": { "tab_size": 2 },
    "YAML": { "tab_size": 2 }
  }
}
```

- `terminal.shell.program` :
  ここでシェルのアプリケーションパスを指定しておくとZedのターミナルパネルを起動時にデフォルトで起動するようになります。  
  パスは環境ごとに異なるので実際のインストールパスを確認してください。  
- `agent` :  
  Agent パネルで普段使いする　AI を設定しておくと、AIに何かお願いする時にパネルを開いてすぐにプロンプト記述作業に入ることができます。
  またAPI利用の場合は、 `Alt+Shift+C` でエージェント設定が簡易にできるので そこからの設定を推奨します。
- `lsp`:
  特に clangd や OmniSharp はバージョンによってオプションが変わるため、Extensionからインストールしたものをそのまま使うことを基本推奨です。  
  またどうしても必要であれば、サーバーアプリケーションをインストール -> 直接参照するように設定しましょう。

## 設定の優先度・反映ルール

1. 設定は「プロジェクト設定」が「グローバル設定」を上書きします。つまりプロジェクトで各項目を指定すれば、そのプロジェクトだけ別挙動にできます。  
2. 大きな変更をグローバルで変更すると、自身の全プロジェクトに影響します。  
3. 変更後は必ず実際に挙動を確認。 問題があれば直ちに元に戻せるようバックアップを取っておきましょう。  

## 実践的な運用例（チームでの共有）

- プロジェクトルートに `settings.json` を置き、リポジトリに含める（ただし機密情報は含めない）  
- 変更履歴はコミットメッセージで明確に（例：「プロジェクト inlay_hints を有効化 — 型ヒントを表示」）  
- 大きなグローバル設定変更（例：デフォルトモデルの変更）は Slack / チャットで告知し、数日間フォールバックプランを用意する

## よくある質問（Q&A）

Q1. 「どこまでプロジェクト側に書くべき？」  
A1. コードの可読性やビルドに関わる挙動はプロジェクト側。 エディタの見た目や個人のキー割当などはグローバルにするのが一般的です。  

Q2. 「エージェント設定に APIキー を含めてもいい？」    
A2. バージョン管理している場所に誤ってアップしたり、漏洩することがない場所で扱うようにしてください。(環境変数やグローバル設定など)  

Q3. 「設定を変更して動かなくなった場合は？」  
A3. バックアップしたものに戻したり、プロジェクト設定を一つずつ戻して挙動を確認してください。  

## まとめ

Zed の `settings.json` は「プロジェクト固有」と「グローバル」で適切に使い分けると非常に強力です  

私のおすすめは  
プロジェクトでは「inlay hints」「file_scan_exclusions」など編集体験に直結する設定を置く  
グローバルでは「ターミナル」「テーマ」「フォント」「Agent デフォルト」を管理することです。
